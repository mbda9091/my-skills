# 方案、执行与验收

围绕同一份方案文档完成需求落地、实施记录和验收对账。原文档是进度与证据的统一入口，小任务简写，大任务才拆阶段；不额外建立审批流、评分体系、独立报告或重复台账。

## 先识别本次意图

| 用户意图 | 行动边界 |
|---|---|
| “你看如何”“是否需要补充”、讨论技能或流程 | 只讨论建议、原因和适用场景，不自动写文件或实施 |
| 根据需求写或完善方案 | 查阅必要代码和资料并写文档，不自动实现 |
| 按文档实施并记录 | 执行授权范围内的实现与必要验证，持续回写 |
| 根据文档验收、没问题就完成 | 检查实现和执行验收，回写结果；发现代码问题先列明，不把纯验收自动扩大成修复授权 |
| 完成整套流程或明确授权修复 | 连续推进编写、实现、修复和验收，无需每阶段重复确认 |

结合会话中已有授权判断，不只按关键词切换模式。用户正在讨论时，即使提到“执行”“skill”，也不代表实施授权。关键歧义影响目标、兼容行为或验收范围时先澄清；普通实现细节自行判断。

## 共用约定

- 先读取项目约定、指定文档及相关 Git 历史，确定本文轮次与待核验版本，再检查对应代码。已有文档不是当前实现的证明；当前代码也不能直接否定旧轮次的完成结果。已有能力直接复用，不为适应最新代码改写旧轮次的目标。
- 默认使用随技能提供的 [方案与迭代记录模板](assets/plan-template.md)。创建新方案或补齐文档结构时读取该文件，替换占位内容，按任务规模简写或删除不适用项；小任务可采用下方最小结构。用户或项目有明确格式要求时优先遵守，不要求仓库另存模板，不为套格式重排整份旧文档。
- 每个验收项应描述可观察的结果，验证它需要的环境及证据。编号、表格与阶段只在便于引用和对账时使用。
- 维护本文轮次内摘要与实施记录的一致性；“当前进展”指本文轮次的进展，不要求历史方案持续描述仓库最新状态。历史事实有误时记录更正，不把后续需求变化当成历史错误。
- 实现和验收中发现范围变化时记录原因与影响。会改变用户目标、兼容承诺或必要验收条件的调整，先讨论，不能靠删除失败项或移出范围制造完成。

## 入口一：根据需求编写文档

结合需求与当前实现，明确问题、范围、方案、验收条件和下一步。区分已有能力、拟实现行为与待验证假设。重点确认“什么结果算完成”，不要把文件数量或编译通过当作业务完成条件。

小任务可将内置模板压缩为以下最小结构：

1. 文首：状态、完成（是/否）、更新日期、完成日期、实现 commit、验收基线。
2. 问题与范围：目标、非目标及完成条件。
3. 方案与执行事项：关键行为、必要异常路径；规模较大时按阶段拆分。
4. 验收项：预期结果、验证方式、当前结果与证据。
5. 实施记录与遗留：按日期记录实际改动、commit、验证结果、范围调整和下一步。

尚未实施或执行验证时明确标注，不预填成功记录。文档本身的撰写完成不代表它描述的实施工作已完成。

## 独立轮次与版本演进

每份文档都有独立使命，须完整包含本轮需求、范围、方案、实际结果、实现 commit 和验收基线。后续可以建设、修改或删除此前功能，但不采用“接替文档”作为补全文档或转移完成责任的机制；链接只用于追溯，不能代替本轮必要内容。

- 复核旧轮次：以该文档的实现/验收提交或产物为对象，按当时约定范围判断。必要时使用隔离检出，不切换或覆盖用户当前工作区。
- 核验当前代码或继续实施旧方案：先查相关文档及 Git 变更，汇总截至目标提交的有效决定。以目标分支已包含的后续明确变更为准；不能只按文件时间、文档排列、SHA 字面大小或其他分支上较新的提交判断先后。分支、合并或 squash 导致对应关系不清时核对实际 diff，不猜测。
- 发现旧文档与当前代码不一致时，先判断是否存在后续有意调整或删除。确认是正常迭代，记录相应提交及原因；只有排除后续变更后，才可判为实现缺损。缺少依据时标记“待核实”，不自动恢复旧行为，即使本次已获一般修复授权，也不能把旧要求当成恢复依据。
- 已完成轮次不会因后续删除功能而变成未完成。例：A 在 `aaa` 建设启动器并验收；B 在后续 `bbb` 明确删除启动器并验收。A、B 都可保持已完成，核验 `bbb` 时不存在启动器是正确结果。
- 旧文档只补可核实的基线；无法确定 SHA 时写“历史基线待核实”，可列候选范围与依据，不伪造精确对应。已有完成记录但原始报告无法回读时，保留“历史记录已完成，本次未回读原始证据”，既不撤销完成，也不声称重新验收通过。新的完成结论仍须满足下方关闭条件。

如项目需要导航，用简短索引记录各轮使命、commit、当轮结果和变更摘要；按 Git 演进及功能支线组织，不引入接替状态或复杂关系台账。

## 入口二：根据文档执行并回写

按上述版本演进规则核对后，从仍有效且尚未完成的事项继续，不重做已有且证据有效的工作，不恢复后续已明确删除的能力。按能独立验证的阶段推进，不要求每次改动都单独立项。

每个有意义的阶段结束后，在原文档记录：

- 实际改动及对应事项；与方案不一致的地方和原因。
- 实现 commit；未提交时写“未提交”，并指明变更范围。
- 实际执行的验证、对象与环境、结果、证据位置及未覆盖边界。
- 尚欠事项及下一步；失败或受阻时记录具体原因与恢复条件。

同步文首、阶段状态与验收表。中途受阻也要保存已有结果，不等全部成功才回写。验证按改动选择必要检查，已通过且无新变化的检查无需重复执行。

## 入口三：根据文档验收与关闭

先明确本次是复核文档当轮结果，还是验证当前版本；结合用户指定提交及上下文判断。未指定时先查版本演进，若不同解释会改变验收标准且仍无法确定，再澄清。逐项比较对应轮次的有效要求、实现与结果，不能将旧方案直接当成当前版本的全部要求。历史证据用于新的验收结论时，必须匹配对象、环境和相关实现，并说明复用依据；无法确认则记录本次未验证，不因此自动推翻原轮次的完成记录。

验收结果使用“通过 / 失败 / 未执行 / 受阻 / 不适用”。不适用须有范围依据；跳过不算通过。编译、加载或模拟测试不能替代文档要求的真实行为验证。

只有以下条件全部满足，才能标记“已完成”、完成“是”，并填写完成日期：

- 文档定义的本轮必要工作已完成，所有必要验收项通过。
- 实现 commit 与验收基线可核对，未把其他提交或产物的结果冒充当前结果。
- 没有未解决的范围内欠项或阻塞问题；可选后续工作明确独立列出，范围调整有记录与相应授权。
- 当前摘要、阶段状态、验收结果和遗留事项彼此一致。

代码未提交时即使本地验收通过，也记录“验收通过，待提交对账”，保留待验收状态和完成“否”。不为关闭文档自动 commit、push、发布或部署；这些动作遵循已有授权。无代码变更的事项写“commit 不适用：具体原因”，不制造提交。

## commit、状态与归档

实现 commit 使用真实可解析的 SHA，推荐完整 SHA；多次提交逐项对应改动，不用分支名、`HEAD` 或文档提交替代实现提交。验收基线单独记录，含未提交改动时注明基线和差异；提交后核对相关差异，必要时复验再关闭。无需在文档中写它自身的提交号，可在后续收尾补齐实现 SHA。

状态描述本文轮次结果；无项目定义时使用：草案、待实施、实施中、待验收、受阻、已暂停、已完成、已取消、已废弃。受阻写解除条件，暂停写恢复条件，取消写原因。完成标记独立记录当轮交付事实；已完成为“是”，已废弃保留此前真实完成情况，不统一改成“否”；后来调整或删除已交付功能，不将原轮次改为已取消或未完成，也不引入“已替代”来覆盖完成事实。

归档是轮次结束后的收尾步骤，独立于工作状态。按项目约定迁移；无约定时将已完成方案移至同级 `archive/`，维护简短索引、文内相对链接及仓库引用，原路径保留跳转说明。不能保留旧章节锚点时注明。当轮未完成即取消的文档也可归档，结果如实保留；已完成后功能被删除的文档仍以原完成结果归档。持续维护的使用指南不归档。

新的建设、调整或删除作为独立轮次记录，可相互引用但各自保持完整。只有明确证据表明原完成判断本身错误，或用户明确要求重开原轮次时，才调整其完成状态，并注明原因与日期；不因后续需求变化或旧临时报告不可访问自动重开。

最终回复只说明文档位置、这次完成的工作、验收结论及仍欠事项，不另造报告。

## 废弃方案

“已废弃”表示用户明确决定不再采用、实施或维护该方案，例如方案复杂且不好用，或宿主已提供所需能力。它与“已取消”（本轮实施任务取消）区分，不等于验收失败，也不以“接替”关系转移文档责任。

收到明确废弃决定后，记录废弃日期、原因、决定来源及此前完成范围；有删除实现的 commit 则列出，没有代码变化则注明不适用，不伪造提交。若尚未实施，完成为“否”、原验收保持未执行；若此前已完成，保留完成标记及历史证据；部分完成按原范围如实记录。

同步文首、摘要、里程碑和待办：原未完成项关闭为“不再实施（已废弃）”，不标成验收通过。保留完整历史设计与结果，但明确禁止按其恢复、继续实现或补验收；只有用户明确重新启用才启动新工作。废弃不自动授权卸载用户环境或删除已有数据。按项目约定可归档为“已废弃”，索引同时保留历史完成情况。

# Set up a Python environment

Create a reproducible Python 3.14 development environment using the rules below. Preserve the project's structure, build backend, and stricter checks where compatible with the migration.

## Python version policy

- Use the latest stable CPython **3.14.x** patch release available at setup time. Check the [official latest Python 3.14 release](https://www.python.org/downloads/latest/python3.14/) before selecting the interpreter. Keep this policy current by resolving the patch version on each setup; do not freeze a historical patch number into this skill.
- Record that exact `3.14.x` version with `uv python pin`. Set `requires-python = ">=3.14,<3.15"` in the root project and each workspace package, Ruff `target-version = "py314"`, and Pyright `pythonVersion = "3.14"`. Align existing CI, container, and editor Python settings with the same policy when they select this project's interpreter.
- Use `uv python install --upgrade 3.14` and `uv python find --managed-python --no-project --show-version 3.14` to install and inspect a managed interpreter. Compare the full version with the official release before pinning it. A minor-version request alone does not prove that an older uv catalog contains the newest patch.
- If uv lacks the latest patch, update uv using its existing installation method within the authorized scope, or report the exact blocker. If dependencies or native extensions cannot support 3.14, resolve the incompatibility or report it; do not silently lower the Python target or move to a different minor release.
- Pin the full version number, not a machine-specific interpreter path. Recreate or resync the project environment with that interpreter as needed. Leave the system Python and global default interpreter unchanged.

## Inspect and choose the shape

Read `AGENTS.md`, `pyproject.toml`, `.python-version`, `uv.lock`, `.gitignore`, package metadata, and existing checks where present. Identify migration constraints, whether the root is installable, where runtime and development dependencies belong, and whether console scripts or multiple packages are needed.

For a new project, choose a single package by default. Use a uv workspace only when independent installable packages or shared code justify it. Treat a non-packaged application as an application; it does not need an artificial distributable package.

## Configure

1. Resolve and pin the interpreter according to the version policy. For an existing project, migrate its Python constraints without overwriting unrelated metadata. For a new project, use `uv init` with the verified interpreter version; select `--package` for installable code or `--no-package` for an application. Create `.python-version`, `pyproject.toml`, and `.gitignore` as appropriate.
2. Put runtime dependencies in the package that imports them. Manage dependencies with `uv add` and `uv remove`; use `uv add --group dev ruff pyright pytest` for the root development tools. Resolve versions that support 3.14 and track the generated `uv.lock`. Preserve existing compatible locked versions; upgrade additional dependencies only when the migration requires it.
3. Configure the checks below at the project root. For an existing project, preserve stricter compatible settings and fix migration failures. Discuss scope if new strict checks would cause a large unrelated rewrite. Keep lint and type-check exceptions narrow and tied to actual files.
4. For installable code, use a `src/<import_name>/` layout unless the project already uses another valid layout. Keep its existing build backend; for a new package, use the compatible backend configuration generated by `uv init --package`. For a CLI, define `[project.scripts]` and verify the installed command.
5. Ignore `.venv/`, `__pycache__/`, `.pytest_cache/`, `.ruff_cache/`, `.pyright/`, `*.egg-info/`, `dist/`, and `build/`. Keep `uv.lock` tracked. Run project commands through `uv run`.

## Shared check configuration

Merge these settings into `pyproject.toml`, adapting paths to the actual source and test directories. Development dependencies belong in `[dependency-groups].dev`, managed by uv.

```toml
[project]
name = "example-project"
version = "0.1.0"
requires-python = ">=3.14,<3.15"
dependencies = []

[tool.ruff]
line-length = 100
target-version = "py314"

[tool.ruff.lint]
select = ["E4", "E7", "E9", "F", "I", "UP", "B"]

[tool.pyright]
include = ["src", "tests"]
pythonVersion = "3.14"
typeCheckingMode = "strict"
venvPath = "."
venv = ".venv"

[tool.pytest.ini_options]
testpaths = ["tests"]
addopts = ["-q"]
```

The project name and version above are examples for new projects; preserve existing metadata. For an application without installable code, set `[tool.uv] package = false` and adapt the check paths instead of inventing a `src/` package.

## Multi-package workspace

Use one root `uv.lock` and root development dependency group. Each installable package under `packages/` owns its metadata, build backend, runtime dependencies, and optional CLI entry points. Every member uses the same Python version policy.

For a root that has no distributable code, add:

```toml
[tool.uv]
package = false

[tool.uv.workspace]
members = ["packages/*"]
```

If the root itself is an installable package, retain its package configuration instead of setting `package = false`. Set Pyright `include = ["packages", "tests"]` for the workspace layout, adding root sources when applicable.

For a member that imports another workspace package, declare that package as a runtime dependency and map it to the local workspace in the consuming member:

```toml
[tool.uv.sources]
shared-package = { workspace = true }
```

Use the actual distribution name for `shared-package`. An aggregate package is optional and only needed when the user wants to install several commands as one distribution; its dependencies and entry points must refer to real members.

## Verify and hand off

Run `uv sync` for a single package, or `uv sync --all-groups --all-packages` for a workspace that installs every member. Use the verified full interpreter version with `--python` when syncing so an older environment cannot silently satisfy the 3.14 range. Then run:

```bash
uv run python --version
uv run ruff check .
uv run ruff format --check .
uv run pyright
uv run pytest
```

Verify that the actual interpreter equals the latest patch selected during setup. Run `uv build` when packaging changes, or `uv build --all-packages` for a workspace; do not build a non-packaged application. For a CLI, run the installed entry point with `uv run <command> --help`, or `uv run --package <member> <command> --help` in a workspace.

Check that the interpreter pin, Python constraints, tool targets, and existing CI/container settings agree. Confirm that `uv.lock` is included in the changes and generated files are ignored. Report the project shape, exact Python version, files changed, and verification results. Report missing tests or blocked checks explicitly rather than claiming they passed.
